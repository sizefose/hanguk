# API-First Audit / Refactor Checklist

## Цель
Убрать бизнес-данные из фронтовых хардкодов и оставить фронт как тонкий слой отображения данных, приходящих из API.

## Чек-лист

- [x] Провести первичный аудит фронта и бэка на наличие статичных бизнес-данных.
- [x] Вынести футер/контакты/ссылки/служебные тексты в API (`/api/site-settings/`).
- [x] Удалить мертвые статичные mock-источники (`src/lib/products.ts`, `src/lib/banners.ts`).
- [x] Добавить единый раздел в админке для управления site settings.
- [x] Включить `Cache-Control: no-store` для динамических API-эндпоинтов каталога и контента.
- [x] Убрать all-or-nothing загрузку на фронте (`Promise.all`) и перейти на частичную деградацию (`Promise.allSettled`).
- [ ] Вынести UI-тексты (лейблы поиска/сортировки/заголовки секций) в отдельный API-конфиг при необходимости мультиязычности.
- [ ] Разделить `src/app/(catalog)/page.tsx` на логические компоненты/хуки (`CatalogHeader`, `CatalogGrid`, `Footer`, `useCatalogData`) для снижения сложности.
- [ ] Добавить smoke-тесты API и E2E-проверки ключевых сценариев (каталог, модалка, фильтры, about, footer).

## Найденные риски и что уже сделано

1. Риск: падение одного API запроса ломало загрузку всего экрана.
   - Исправление: загрузка контентных блоков и каталога переведена на `Promise.allSettled`.

2. Риск: часть ответов API могла кэшироваться браузером/прокси и отдавать устаревшие данные.
   - Исправление: добавлен `Cache-Control: no-store, no-cache, max-age=0` в views каталога/контента.

3. Риск: админка могла падать до миграций при проверке singleton-настроек.
   - Исправление: `has_add_permission` в `CatalogFilterSettingsAdmin` защищен от `ProgrammingError/OperationalError`.

- Реорганизовать большой клиентский файл каталога в небольшие модули без изменения поведения.
- Опционально вынести текстовые UI-константы в API (если это реально нужно бизнесу, а не только разработке).
