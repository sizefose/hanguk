# Hanguk 2.0: Архитектура проекта и журнал ошибок

Документ собран по итогам текущего большого цикла разработки и отладки.
Цель: зафиксировать структуру проекта, объяснить ключевые термины и сохранить разбор проблем/решений, чтобы не повторять один и тот же класс багов.

---

## 1) Структура проекта

### 1.1 Корень репозитория

- `backend/` — Django + DRF API + админка + модели + миграции.
- `src/` — Next.js frontend (App Router) + UI-компоненты.
- `public/` — статические ассеты фронта (иконки, картинки).
- `docker-compose.yml`, `docker-compose.backend.yml`, `Dockerfile` — контейнеризация.
- `package.json` — фронтовые скрипты (`dev`, `build`, `lint`).

### 1.2 Backend (Django)

- `backend/config/` — настройки Django и маршруты проекта.
- `backend/catalog/` — каталог товаров:
  - модели: товары, категории, страны, баннеры, скидочные группы;
  - API-сериализаторы и вьюхи;
  - бизнес-логика скидок;
  - админка.
- `backend/content/` — контентные сущности:
  - секции “О нас”, hero-блок, табы, карта.
- `backend/catalog/migrations/`, `backend/content/migrations/` — история схемы БД.
- `backend/media/` — загружаемые файлы (изображения товаров, категорий, баннеров и т.д.).

### 1.3 Frontend (Next.js, App Router)

- `src/app/layout.tsx` — корневой layout.
- `src/app/(catalog)/page.tsx` — главная страница каталога (фильтры, сортировка, товары, пагинация, контентные блоки).
- `src/app/(catalog)/layout.tsx` — layout каталога с параллельным слотом модалки.
- `src/app/(catalog)/@modal/(.)p/[slug]/page.tsx` — intercepted route модалки товара.
- `src/app/(catalog)/@modal/default.tsx` — пустой default для modal-slot.
- `src/app/(catalog)/@modal/[...catchAll]/page.tsx` — catch-all для очистки modal-slot.
- `src/app/p/[slug]/page.tsx` — страница для прямых ссылок на товар (редирект-логика).
- `src/components/BottomSheet.tsx` — унифицированный компонент модалки/шторки.
- `src/app/globals.css` — глобальные стили.

## 2) Как устроен поток данных

1. Фронт открывает каталог и читает query-параметры (`category`, `country`, `q`, `sort`, `page`).
2. Отправляются запросы в API:
   - список товаров;
   - доступные опции фильтров;
   - баннеры/рекомендации/контентные секции.
3. UI обновляет карточки, фильтры, пагинацию.
4. Клик по товару открывает модалку через intercepted route `/p/[slug]`.
5. Закрытие модалки возвращает пользователя в состояние каталога (тот же query, фильтры, скролл).

## 3) Словарь терминов (с объяснением)

### SSR и Hydration

- **SSR (Server-Side Rendering)**: HTML генерируется на сервере.
- **Hydration**: React на клиенте “подключается” к уже отданному HTML.
- Ошибка “Hydration failed” появляется, если сервер и клиент рассчитали разный initial state.

### App Router, Parallel Routes, Intercepted Routes

- **App Router**: система маршрутизации Next.js через папки `app/`.
- **Parallel Routes** (`@modal`): дополнительный “слот” UI, рендерится параллельно основному контенту.
- **Intercepted Route** (`(.)p/[slug]`): маршрут, который перехватывается и показывается как модалка поверх текущей страницы, а не как полный переход.

### Soft Navigation vs Hard Reload

- **Soft navigation**: переход внутри Next Router без полной перезагрузки страницы.
- **Hard reload/navigation**: браузер перезагружает документ целиком (потеря клиентского состояния, видимые “мигания”).

### `router.push`, `router.replace`, `router.back`

- `push`: добавляет запись в историю.
- `replace`: заменяет текущую запись в истории.
- `back`: шаг назад по истории браузера.

Почему важно: для modal-route выбор между `replace/back` критичен, иначе слот модалки может остаться в неконсистентном состоянии.

### Body Scroll Lock

- При открытой модалке `document.body.style.overflow = "hidden"` и `touchAction = "none"` блокируют прокрутку фона.
- Если lock не снять при закрытии — интерфейс выглядит “мертвым”.

### `pointer-events`

- CSS-свойство, определяет, перехватывает ли элемент клики.
- Неверное значение у overlay в момент закрытия может:
  - либо блокировать всю страницу,
  - либо пропускать клики “сквозь модалку” и запускать гонки роутинга.

## 4) Журнал ошибок и решений

Ниже зафиксированы ключевые инциденты по проекту (не косметика, а те, что ломали поведение/стабильность).

### Инцидент A: `ModuleNotFoundError: No module named 'django'`

Симптом:
- `python3 manage.py migrate` не запускался локально.

Причина:
- Команда выполнялась вне окружения с установленными зависимостями backend.

Решение:
1. Активировать виртуальное окружение backend (или запускать через Docker backend-контейнер).
2. Установить зависимости из `requirements` (если локально).
3. Повторить `python3 manage.py migrate`.

---

### Инцидент B: `ProgrammingError ... content_herosection doesn't exist`

Симптом:
- Падение админки `/admin/` с ошибкой отсутствующей таблицы.

Причина:
- Модель добавлена, а миграция не применена к БД.

Решение:
1. Проверить наличие миграции (`backend/content/migrations/0003_herosection.py`).
2. Выполнить миграции (`manage.py migrate`) в нужном окружении БД.
3. Проверить, что контейнер/локальная БД одна и та же.

---

### Инцидент C: `ValueError make_aware expects a naive datetime`

Симптом:
- Падение при создании discount group в админке.

Причина:
- В коде выполнялся `make_aware` для datetime, который уже был timezone-aware.

Решение:
1. Перед `make_aware` проверять, наивная дата или aware.
2. Не “aware-ить” повторно.
3. Привести весь pipeline скидок к единому timezone (в проекте — МСК).

---

### Инцидент D: CSS build error `Unexpected token Semicolon`

Симптом:
- Падение сборки фронта на `globals.css`.

Причина:
- Обрыв/повреждение блока `@media` (пустой/незакрытый блок).

Решение:
1. Проверить конец файла CSS.
2. Закрыть/удалить некорректный media block.
3. Перепроверить `npm run build`.

---

### Инцидент E: Hydration mismatch на кнопках фильтра

Симптом:
- `Hydration failed` + отличие текста/класса кнопки “Категории”.

Причина:
- Клиентский state фильтров отличался от серверного на первом рендере.

Решение:
1. Инициализацию фильтров из `window/sessionStorage` делать только после mount.
2. Не рендерить клиентозависимые вычисления до bootstrapping.
3. В URL/state синхронизацию добавить guard от лишних перерендеров.

---

### Инцидент F: Неактуальные плашки скидок в фильтрах (категории/страны)

Симптом:
- После правки discount group плашки не снимались/не обновлялись в фильтрах.

Причина:
- Неполная реактивность: обновлялась одна сторона (страны) и “залипала” вторая (категории), либо обновление зависело от локального state без запроса свежих данных.

Решение:
1. Централизовать пересчет опций фильтров на backend (`/filter-options`).
2. На фронте всегда перезабирать filter options при изменении активных фильтров и refresh-токена.
3. Свести обе стороны (категории/страны) к одной схеме обновления.

---

### Инцидент G: Пагинация показывала неверные номера страниц

Симптом:
- На некоторых страницах отображался нелогичный набор кнопок (`...` в неправильном месте).

Причина:
- Ошибка правил формирования диапазона pagination items.

Решение:
1. Зафиксировать правило: всегда показывать первую/последнюю + соседние + `...` по условиям.
2. Ограничить максимальное “окно” кнопок (по текущему решению — 7).
3. Синхронизировать с query `?page=`.

---

### Инцидент H: Блокирующий оверлей после закрытия модалки (интерфейс не кликается)

Симптом:
- После закрытия модалки UI переставал реагировать на клики до перезагрузки.

Причина:
- Несогласованность состояния `BottomSheet` + состояния modal-slot.
- При certain race модалка визуально уходила, но логика закрытия/размонтирования не завершалась корректно.

Решение:
1. Добавлен fail-safe reset state в `BottomSheet` после `onRequestClose`.
2. Добавлен body unlock fallback.
3. Убраны/скорректированы click-through состояния overlay во время close.

---

### Инцидент I: “Тот же товар не открывается повторно”

Симптом:
- После закрытия товара A повторный клик по A меняет URL, но модалка не открывается.
- Другой товар B открывается.

Причина (комбинация):
1. Ранее использовался `window.history.replaceState(null, ...)`, что ломало внутреннее состояние Next Router.
2. Закрытие modal-route делалось не всегда через подходящий механизм для intercepted route.
3. Быстрые клики создавали гонку между закрытием и новым открытием.

Решение:
1. Убрать `window.history.replaceState` и использовать `router.replace`.
2. Для модалки реализовать стратегию close:
   - `router.back()` если модалка открыта из каталога;
   - fallback на `router.replace(target)` если `back` не вывел из `/p/...`.
3. Добавить marker “opened from catalog”.
4. Добавить антидребезг и явный `preventDefault + router.push` на карточках.

---

### Инцидент J: Быстрые клики по модалке вызывали перезагрузку страницы

Симптом:
- При частых/быстрых кликах наблюдался hard reload.

Причина:
- Конкуренция нативного перехода `<a>` и программного роутинга при смене состояния модалки.

Решение:
1. Перехват клика (`event.preventDefault()`).
2. Программный переход `router.push(...)`.
3. Антидребезг повторных открытий по тому же slug.

## 5) Почему долго “ходили по кругу”

Проблема была не в одной строке, а в пересечении 4 подсистем:

1. App Router (intercepted/parallel route).
2. История браузера и способ закрытия (`back/replace`).
3. Локальная синхронизация URL параметров каталога.
4. Жизненный цикл `BottomSheet` (scroll-lock, pointer-events, isClosing).

Если фиксить только одну подсистему, баг переезжал в другую форму.

## 6) Текущее стабильное правило для модалки товара

1. Открытие из каталога:
   - сохранить return URL каталога;
   - поставить marker открытия из каталога;
   - открыть `/p/[slug]` через router.

2. Закрытие:
   - если marker есть: `router.back()`;
   - если после таймаута все еще `/p/...`: `router.replace(returnUrl)`.

3. Прямой вход по ссылке:
   - marker не ставится;
   - закрытие делает `replace` в каталог.

6. Проверить пагинацию на первых, средних и последних страницах.

## 10) Тех-конспект (обновлено 2026-03-03)

### 10.1 Текущая структура под масштабирование доставки

- Frontend:
  - основной экран и большая часть UI живут в `src/app/(catalog)/page.tsx`;
  - глобальные стили сосредоточены в `src/app/globals.css`;
  - фронт получает общий `site-settings` без сущностей "магазин -> доставки".
- Backend:
  - `SiteSettings` и `StoreContact` в `backend/content/models.py` уже дают список адресов/телефонов;
  - API отдает их через `SiteSettingsSerializer` (`backend/catalog/serializers.py`);
  - админка уже поддерживает редактирование `StoreContact` через inline в `backend/content/admin.py`.

### 10.2 Масштабируемость (что хорошо / что ограничивает)

Плюсы:
- Есть отдельная модель магазинов (`StoreContact`) вместо жестко захардкоженных полей;
- Сериализатор уже делает fallback со старой схемы на новую, что снижает риски миграции;
- Контентные блоки разделены по endpoint-ам (`/site-settings/`, `/about-section/`, etc.), можно эволюционировать независимо.

Ограничения:
- Нет нормализованной модели "сервис доставки" и связки M2M с конкретным магазином;
- Нет полей для URL страницы магазина в сервисе доставки и отдельного map script на магазин/доставку;
- `src/app/(catalog)/page.tsx` перегружен ответственностями (каталог + фильтры + контент + footer + about), при росте фич будет расти сложность.

### 10.3 Что сделано в рамках задачи 1

- На фронте добавлен блок выбора адреса (dropdown) + отображение доступных иконок доставок после выбора.
- Реализация пока на временной мапе (`ADDRESS_DELIVERY_PRESETS`) в `src/app/(catalog)/page.tsx`, т.к. API ещё не хранит доставки по магазинам.
- Добавлены иконки сервисов:
  - `public/static/icons/delivery/chibbis.svg`
  - `public/static/icons/delivery/yandex-food.svg`
  - `public/static/icons/delivery/pickup.svg`

### 10.4 Рекомендуемый следующий шаг для роста без техдолга

1. Вынести доставку в отдельные модели:
   - `DeliveryService` (тип, иконка, признак активности),
   - `Store`/`StoreContact` (адрес, телефон),
   - `StoreDelivery` (store_id, service_id, external_url, map_script_url, sort_order, is_active).
2. Расширить `/site-settings/` или сделать отдельный endpoint `/stores/`.
3. Перенести delivery UI в отдельный компонент `src/components/DeliverySelector.tsx`.
